# 🕊️ Parley — Project Roadmap

## 1. Overview

Parley is a local, single-user Laravel app where multiple AI agents talk to each other in a group chat. The user creates agents, groups them into chats with per-chat initial prompts, then either lets them auto-converse up to a message budget, or advances the conversation one message at a time. Everything (messages, tokens, cost, latency) is stored in the database. **For this MVP => No auth, no streaming, no images — text only.**

## 2. Tech Stack

- **Backend:** Laravel (latest), Eloquent + MariaDB, openai-php/laravel package for API calls
- **Queue:** `database` driver + `queue:work` for turn processing and retries
- **Frontend:** Blade + Tailwind CSS + Alpine.js, minimal modern dark theme. No SPA framework, no websockets — **polling every 10 seconds**
- **Real-time:** frontend polls a JSON endpoint with the last-seen message ID; backend returns only newer messages

## 4. Core Mechanics

### 4.1 Context Building (role-per-perspective)
When it's an agent's turn, build the messages array **at call time** (never store a fixed role):

1. `system` = `chat_agent.initial_prompt` ?? `agent.default_system_prompt` (omit if both empty)
2. Walk chat history in order:
   - Agent's **own** past messages → `role: "assistant"`, raw content
   - **Everyone else's** messages → `role: "user"`, content prefixed `[SpeakerName]: ...`

**Caching friendliness (important):** history is append-only — never rewrite or reorder past messages, keep the system prompt string and the `[Name]: ` prefix format perfectly stable, and keep request params consistent. This lets provider-side prompt caching hit on long chats. If the user edits an initial prompt mid-chat, just apply it from the next turn — no need to preserve a cache hit.

### 4.2 Turn Engine

One queued job, `ProcessTurnJob(chat_id, manual = false)`:

- Middleware: `WithoutOverlapping` keyed on `chat:{id}` → guarantees **one in-flight turn per chat**
- If chat status ≠ `running` and not `manual` → exit silently
- If `running` and `message_count >= message_limit` → set status `idle`, exit (budget reached)
- Pick next speaker: active chat agents sorted by `position`; next = first agent positioned **after the last message's sender**, wrapping around
- Build context (§4.1), call `POST {base_url}/chat/completions` via `Http::withToken(api_key)->timeout(...)`, measure latency with `microtime(true)`
- Save message with content, token usage, computed cost, latency, model
- **Auto mode:** if status is still `running` → if new count ≥ `message_limit` set `idle`, else re-dispatch `ProcessTurnJob` with ~1–2s delay. **Manual mode:** done, status stays `idle`

### 4.3 Auto-Run Start/Stop
- **Start** (only from `idle`): `message_limit = current_message_count + auto_budget`, `status = running`, dispatch first turn
- **Stop** button: `status = idle`. (In-flight job exits on next guard check.)

### 4.4 Retries & Failure
- Job has `tries = 3`, backoff e.g. `5, 15, 30` seconds (Laravel handles retries for free — timeouts, 5xx, connection errors all count)
- On final failure (`failed()`): `status = error`, store `last_error` + `error_agent_id`, UI shows a red banner with the failing agent and error text, plus a "Reset to idle" button

## 5. Routes / Endpoints

**Pages (Blade):**
- `GET /` → chats list (dashboard)
- `GET/POST /agents`, `GET/PUT /agents/{id}`, `DELETE` — agent management pages
- `GET /chats/create`, `GET /chats/{id}` — chat view (messages + controls)
- `POST /chats/{id}/agents`, `PUT /chats/{id}/agents/{pivot}`, `DELETE ...` — attach/edit/detach chat agents (edit = change prompt, position, or swap agent)
- `POST /chats/{id}/start` · `POST /chats/{id}/stop` · `POST /chats/{id}/next`

**JSON (for polling & forms):**
- `GET /api/chats/{id}/messages?after={lastMessageId}` → `{ messages: [...], status, message_limit, message_count }` — returns messages with `id > after` (all messages when `after=0`)
- `POST /agents/{id}/test` (optional nicety) — sends a 1-token ping to verify endpoint/key/model

## 6. Frontend Spec

- **Layout:** single-page chat view, dark minimal modern design (Tailwind), generous whitespace, rounded bubbles
- **Message bubbles:** colored per agent (agent's `color`), agent name + model in the header, content below, tiny meta footer: `⚡ 840ms · ↑1.2k ↓340 tok · $0.0031`
- **Controls bar (top of chat):** status pill (idle/running/error), Start Auto / Stop button, "Next message ▶" button (enabled only when `idle`), auto-budget input (default 20), chat agents panel — add/remove/**swap** agents, edit per-chat prompts, reorder
- **Polling JS (Alpine):** every 10s call the `after=` endpoint, append new messages, update status/controls; full history on initial load. Pause polling when tab hidden (optional)
- **Stats footer (per chat):** total messages, total tokens, total cost, avg latency
- Empty states, loading states, and validation errors styled properly

## 7. Implementation Phases (build in this order)

1. **Scaffold** — Laravel app, DB config (`QUEUE_CONNECTION=database`), Tailwind + Alpine via Vite, base layout, all migrations + models + relations
2. **Agents CRUD** — full UI + validation + test-connection endpoint
3. **Chats & chat agents** — create chat (pick agents, order, initial prompts), edit/swap mid-chat
4. **Manual turn engine** — `ProcessTurnJob`, context builder, API call, message save with metadata. "Next message" button works; messages visible on reload
5. **Polling** — JSON endpoint + Alpine polling + live message append + status sync
6. **Auto-run** — start/stop, budget/limit logic, self-re-dispatch loop, `WithoutOverlapping`
7. **Hardening** — retries, `failed()` → error status + banner + reset button, edge cases below
8. **Polish** — per-chat stats, cost display, final UI pass

## 8. Edge Cases to Handle

- Only one turn in flight per chat (overlapping lock) — starting auto or clicking Next while `running` must be rejected
- Swapping an agent mid-chat: deactivate old pivot (`active=false, left_at=now`), add new one; old agent's messages become `user`-role history for the new agent
- A chat with < 2 active agents can't start auto-run
- Round-robin wrap-around and "chat with no messages yet" (first speaker = lowest position)
- Keep the last N messages configurable later — for v1 send full history (note as future work if context windows bite)

## 9. Acceptance Checklist

- [ ] Two agents with different endpoints/prompts converse in round-robin
- [ ] Auto-run stops exactly at `start_count + auto_budget` messages
- [ ] Stop button halts the loop; Next advances one message
- [ ] Agent fails → 3 retries → chat `error` with reason + reset button
- [ ] Agent swap mid-chat continues conversation seamlessly
- [ ] New messages appear within ~10s without reload
- [ ] Every message stores tokens, latency, cost; chat shows aggregates
- [ ] Long chats hit provider prompt caching (stable prefix, append-only history)
